Diagnóstico: lo que ya existe en Supabase

Revisé el repositorio antes de proponer nada. Este es el esquema real que usa la app hoy — el dashboard se construye sobre esto, no sobre una tabla ideal imaginaria.

Tablas activas (referenciadas en Admin/Admin.js, Admin/Admin_cms.js, Forms/form.js, Login/*.js):

TablaQué guardaCampos clave detectados
solicitudes Cada solicitud de asesoría enviada desde el formulario público id, usuario_id, nombre_completo, cedula, telefono, correo, parroquia, descripcion, es_anonimo, estado, tipo_asesoria, creado_en, asignada_a, asignada_por
perfiles Usuarias registradas + equipo (admin / asesora / usuaria) id, rol, nombre_completo, nombre_usuario, email, telefono
notas_solicitud Notas internas del equipo sobre una solicitud solicitud_id, contenido, creado_en
publicaciones Contenido editorial del CMS (semanario / noticiero) titulo, tipo, publicado, fecha
configuracion_visual, push_subscriptions Tema visual estacional y suscripciones push — sin valor analítico directo para este dashboard
!

Hallazgo clave que condiciona todo el diseño: cuando es_anonimo = true, Forms/form.js guarda parroquia = null y no pide nombre, cédula ni correo. Es decir: las solicitudes anónimas no tienen ubicación geográfica. No es un bug — es una decisión de privacidad correcta — pero significa que cualquier mapa o gráfico "por parroquia" excluye por diseño a una parte de las usuarias. Lo vas a ver marcado en los KPIs más abajo.

Audiencia y propósito

Antes de abrir Power BI: quién lo mira y qué decisión toma con lo que ve.

Vista Directiva

Quién: coordinación de IMMUJEL (rol admin)

Frecuencia: semanal / mensual

Decisión que habilita: ¿dónde reforzar cobertura territorial? ¿hay cuellos de botella en el proceso? ¿se necesita más personal asesor?

Vista Operativa

Quién: asesoras (rol asesora)

Frecuencia: diaria

Decisión que habilita: ¿qué caso asignado a mí sigue pendiente? ¿cuál lleva más tiempo esperando respuesta?

En Power BI esto no exige dos archivos distintos: se resuelve con dos páginas dentro del mismo reporte (pestañas abajo del lienzo), cada una con su propio filtro por defecto. Lo verás en el paso 5.

Arquitectura técnica

Supabase ya es Postgres — Power BI se conecta directo, sin exportar nada a mano.

Esto es información de personas en situación de violencia — trátala con ese peso.

Antes de conectar Power BI, crea en Supabase un rol de Postgres de solo lectura, separado del usuario que usa la app, con permisos únicamente sobre una vista que ya excluya columnas sensibles (cédula, teléfono, correo, descripción libre). El panel admin ya controla acceso por rol vía la app — el reporte de Power BI necesita su propio control, porque una vez publicado en el workspace, cualquiera con acceso al workspace ve todo lo que la vista expone.

Vista de solo lectura recomendada (ejecutar una vez en el SQL Editor de Supabase):

-- Vista sin columnas identificables, para el dashboard agregado
create view public.v_dashboard_solicitudes as
select
  id,
  case when es_anonimo then null else parroquia end as parroquia,
  estado,
  tipo_asesoria,
  es_anonimo,
  creado_en,
  asignada_a,
  asignada_por
from public.solicitudes;

-- Rol de solo lectura para Power BI
create role dashboard_ro login password 'usa-un-secreto-fuerte-aqui';
grant usage on schema public to dashboard_ro;
grant select on public.v_dashboard_solicitudes to dashboard_ro;
grant select on public.perfiles to dashboard_ro; -- solo id, rol, nombre_completo, nombre_usuario

Guarda esa contraseña como variable de entorno, nunca en un archivo del repositorio ni en el propio reporte de Power BI.

¿Para qué serviría Python aquí? No es obligatorio — Postgres puede resolver el refresco solo con pg_cron — pero es útil si más adelante quieres alertas automáticas o exportar históricos. Detalle en el paso 6.

5

Power BI, paso a paso

De cero al reporte publicado. Hazlo en este orden — cada paso depende del anterior.

  1. 1. Instala Power BI Desktop (gratis, solo Windows) desde Microsoft Store o powerbi.microsoft.com. No necesitas licencia Pro para diseñar; la pedirás más adelante solo para publicar y compartir.
  2. 2. Obtén las credenciales de conexión — en Supabase: Project Settings → Database → Connection string. Copia host, puerto (usa el connection pooler, puerto 6543, para conexiones tipo BI), nombre de base de datos y el usuario/contraseña del rol dashboard_ro que creaste en el paso 4.
  3. 3. Conecta: Obtener datos → Base de datos PostgreSQL. Pega host y puerto. En modo de conectividad elige Importación (más simple para empezar; DirectQuery lo dejas para cuando el volumen de datos crezca). Autentica con dashboard_ro.
  4. 4. Selecciona las tablas: v_dashboard_solicitudes, perfiles, notas_solicitud. No selecciones solicitudes directamente — usa la vista filtrada.
  5. 5. Power Query (Transformar datos): convierte creado_en a tipo Fecha/Hora, crea una columna calculada Mes = Date.StartOfMonth([creado_en]), y renombra columnas a etiquetas legibles para quien lea el reporte (ej. estado → "Estado de la solicitud").
  6. 6. Modelo de datos (vista Modelo): crea la relación v_dashboard_solicitudes[asignada_a] → perfiles[id]. Añade una tabla Calendario (Modelado → Nueva tabla → Calendario = CALENDAR(MIN(v_dashboard_solicitudes[creado_en]), TODAY())) y márcala como tabla de fechas — esto habilita comparaciones "vs. mes anterior".
  7. 7. Medidas DAX (Modelado → Nueva medida): 
    Total Solicitudes = COUNTROWS(v_dashboard_solicitudes)

% Anonimas =
DIVIDE(
    CALCULATE([Total Solicitudes], v_dashboard_solicitudes[es_anonimo] = TRUE),
    [Total Solicitudes]
)

Tasa Finalizacion =
DIVIDE(
    CALCULATE([Total Solicitudes], v_dashboard_solicitudes[estado] = "finalizado"),
    [Total Solicitudes]
)

Pendientes Mas 7 Dias =
CALCULATE(
    [Total Solicitudes],
    v_dashboard_solicitudes[estado] = "pendiente",
    DATEDIFF(v_dashboard_solicitudes[creado_en], TODAY(), DAY) > 7
)
  8. 8. Construye los visuales siguiendo el wireframe del paso 3. Aplica la misma paleta en todo el reporte: un color principal para datos neutros, y semáforo (verde/ámbar/rojo) reservado únicamente para estado — nunca lo mezcles con el color de marca.
  9. 9. Publica (Inicio → Publicar) a un workspace privado de IMMUJEL en Power BI Service, no a "Mi área de trabajo" personal. Configura la actualización programada (Configuración del conjunto de datos → Actualización programada) — con el plan gratuito puedes programar hasta 8 veces al día.
  10. 10. Restringe el acceso compartiendo el workspace solo con las cuentas reales de admin/asesoras. Si quieres que cada asesora vea únicamente sus casos asignados en la Página 2, usa Seguridad de nivel de fila (RLS) de Power BI filtrando por asignada_a.
6

Automatización con Python (opcional)

Tiene sentido si quieres alertas automáticas o históricos versionados fuera de Supabase. Si solo necesitas que el número se actualice solo, pg_cron dentro de Postgres ya lo resuelve sin escribir una línea de Python.

Opción simple — sin Python

Extensión pg_cron de Supabase para refrescar una vista materializada cada noche:

select cron.schedule(
  'refresh_dashboard',
  '0 3 * * *',
  $$ refresh materialized view v_dashboard_resumen $$
);

Opción con Python

Útil para: alertas por correo de casos vencidos, exportar snapshots a CSV, o lógica que no cabe en SQL puro.

Ejemplo mínimo — alerta de solicitudes pendientes hace más de 7 días, pensado para correr con el Programador de tareas de Windows una vez al día:

import os
import psycopg2

# Nunca hardcodees credenciales: usa variables de entorno
DB_URL = os.environ["DASHBOARD_RO_DATABASE_URL"]

QUERY = """
    select count(*) from v_dashboard_solicitudes
    where estado = 'pendiente'
      and creado_en < now() - interval '7 days'
"""

def main():
    with psycopg2.connect(DB_URL) as conn:
        with conn.cursor() as cur:
            cur.execute(QUERY)
            (vencidas,) = cur.fetchone()

    if vencidas > 0:
        print(f"Alerta: {vencidas} solicitudes pendientes hace mas de 7 dias")
        # aqui iria el envio de correo/webhook, ej. con smtplib o una integracion de Slack

if __name__ == "__main__":
    main()

Programa el script con el Programador de tareas de Windows (búscalo en el menú inicio) apuntando a python alerta_pendientes.py, una vez al día en la madrugada.

7

Viabilidad: seguimiento de casos de violencia de género

La pregunta real que estás haciendo: ¿aguanta esta estructura convertirse en seguimiento de casos, no solo de solicitudes iniciales?

Veredicto: técnicamente viable, sin reescribir nada — pero hoy solicitudes modela un contacto puntual, no un caso con historia. Cuando alguien vuelve a necesitar ayuda, o su situación escala, no hay dónde registrar esa evolución más allá de una nota de texto libre en notas_solicitud.

Qué le falta al esquema actual para sostener seguimiento real de casos:

NecesidadPor qué importa
Historial de cambios de estado (con fecha)Hoy solo existe el estado actual — no puedes medir tiempo de respuesta ni reconstruir qué pasó, y es el dato que un ente externo (fiscalía, tribunal) puede pedir
Tipificación del tipo de violenciaFísica, psicológica, patrimonial, sexual, según la Ley Orgánica sobre el Derecho de las Mujeres a una Vida Libre de Violencia — sin esto no puedes reportar por tipo, que suele ser el dato que piden instancias municipales/estadales
Nivel de riesgo / urgenciaSin un campo de riesgo, un caso grave se ve igual que una consulta general en la lista de trabajo de la asesora
Medidas de protección solicitadas/otorgadasEs información operativa que un caso de violencia de género típicamente necesita rastrear
Vínculo con otros entes (CICPC, Fiscalía, tribunales)Para saber si el caso ya escaló fuera de IMMUJEL

⚑
Antes de construir esto, no después.

Ampliar el detalle de un caso de violencia de género implica guardar más información sensible en más lugares. Antes de crear estas tablas: define una política de acceso y retención de datos, considera orientación legal sobre manejo de datos de sobrevivientes, y decide quién exactamente puede ver el detalle completo de un caso (probablemente no todo el equipo, ni siquiera todas las asesoras). Esto no es un paso técnico — es una decisión institucional que debería tomar quien dirige IMMUJEL, no algo que se resuelve solo con permisos de Postgres.

Ruta recomendada, en orden:

  1. Lanza primero el dashboard agregado de este documento (pasos 0 a 6) — es útil de inmediato y no expone nada nuevo.
  2. En paralelo, define con el equipo directivo la política de acceso a datos de casos.
  3. Con esa política aprobada, agrega historial_estados (la pieza de menor riesgo y mayor valor: desbloquea el KPI de tiempo de resolución sin tocar datos sensibles nuevos).
  4. Recién después, evalúa casos, tipificación y medidas de protección, con RLS de Supabase activado desde el día uno de esas tablas.

Viabilidad: módulo de publicaciones

Viable ahora mismo, baja prioridad

publicaciones (semanario/noticiero, con bandera publicado) es contenido editorial simple, sin datos sensibles. Es la extensión de menor esfuerzo: una tercera página en el mismo reporte de Power BI con "publicaciones por mes", "% en borrador vs. publicado" y "ritmo editorial por tipo". Tiene sentido agregarla cuando el dashboard principal ya esté estable — no compite en prioridad con el seguimiento de asesorías, que es el propósito central de IMMUJEL.
